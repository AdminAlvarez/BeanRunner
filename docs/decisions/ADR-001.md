# ADR-001: Selección del Lenguaje de Programación Base y Estándar C

## Estado
Aceptado

## Contexto y Problema
El desarrollo del servicio JobRunner requiere interactuar de forma directa con las llamadas al sistema operativo Linux para la gestión de procesos (`fork`, `execvp`, `waitpid`), manejo de señales (`SIGTERM`, `SIGKILL`), redirección de descriptores de archivo (`dup2`, `pipe`) y comunicación por red mediante sockets TCP (`socket`, `bind`, `listen`, `accept`). Se debe seleccionar un lenguaje que garantice portabilidad, control absoluto sobre los recursos del sistema y compilación reproducible sin advertencias.

## Alternativas Consideradas

### Alternativa A: C puro (Estándar C11) con llamadas POSIX.1-2008
* **Ventajas:** Acceso nativo y sin sobrecarga a la API POSIX de Linux; control explícito sobre la memoria y descriptores de archivo; alta compatibilidad con herramientas de análisis dinámico (`valgrind`, `gdb`); compilación limpia e hiperestricta mediante GCC/Clang.
* **Desventajas:** Requiere gestión manual estricta de memoria (`malloc`/`free`) y manipulación manual de cadenas de caracteres, aumentando la probabilidad de fugas de memoria si no se audita adecuadamente.

### Alternativa B: C++ moderno (Estándar C++17)
* **Ventajas:** Disponibilidad de abstracciones orientadas a objetos, gestión automática de memoria mediante punteros inteligentes (`std::unique_ptr`), colecciones estándar (`std::vector`, `std::map`) y manejo de excepciones.
* **Desventajas:** Las abstracciones de C++ agregan complejidad innecesaria al interactuar con llamadas C puras de POSIX; riesgo de manejo inadecuado de excepciones en entornos multiproceso (`fork`); mayor consumo de recursos implícito.

## Decisión Seleccionada
Se selecciona la **Alternativa A: C puro (Estándar C11) con POSIX.1-2008**. La arquitectura del proyecto requiere operar como un demonio de bajo nivel en Linux. La simplicidad de C11 combinada con las llamadas nativas de POSIX permite un control directo sobre la creación de procesos y sockets, alineándose estrictamente con los conocimientos del equipo Beanner.

Flags obligatorios de compilación en el `Makefile`:
`-std=c11 -Wall -Wextra -Werror -pedantic -D_POSIX_C_SOURCE=200809L`

## Consecuencias y Riesgos
* **Positivas:** Cero sobrecarga de ejecución; control absoluto de recursos de red y memoria; cumplimiento estricto de compilación sin advertencias.
* **Negativas:** La manipulación de cadenas y estructuras debe programarse cuidadosamente.
* **Mitigación de Riesgo:** Se integrará `valgrind` en la suite de pruebas automatizadas para detectar cualquier fuga de memoria o descriptor sin cerrar antes de realizar integraciones a la rama principal.

## Requisitos Afectados
* RNF-01: Compilcompilación y ejecución en Linux declarada.
* RNF-02: Construcción reproducible mediante clon limpio.
* RNF-17: Organización en módulos con responsabilidades identificables.
* RNF-19: Compilación sin advertencias bajo banderas estrictas.

## Evidencia y Prototipo
Prototipo verificado compilando un esqueleto modular en C11 usando `gcc -std=c11 -Wall -Wextra -Werror -pedantic` sin generar ninguna advertencia.
